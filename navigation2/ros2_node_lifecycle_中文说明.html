ROS 2 Managed Node 生命周期设计

根据 ROS 2 Design 文档《Managed nodes》（原文编写于 2015 年，2021 年修订）整理。

一句话概括：Managed node 把节点的内部实现封装成黑盒，只对外提供一套标准的生命周期状态和管理接口。外部监督器据此完成启动、配置、运行、暂停、恢复、故障处理和销毁。

二、状态机的设计理念

1. 外部监督，节点自治受限

主状态的离开通常需要外部 supervisor 的明确动作；这样 launch、编排器或恢复工具可以统一决定何时启动和停止组件。设计文档特别提醒：自管理虽然可行，但可能干扰外部管理逻辑。

2. 配置与运行分离

Inactive 是关键缓冲区：节点已完成配置但不处理业务数据。可以在不改变运行行为的情况下重新配置资源，再由 activate 进入工作态。

3. 可观测、可预测、可恢复

每次转换都应报告结果，并通过生命周期状态事件广播新状态。失败可以回到 Unconfigured；无法清理时进入终态 Finalized，保留调试和 introspection 的机会。

4. 稳定的公共契约

管理工具不需要了解节点内部实现，只需依赖固定状态、转换、服务和状态事件。更复杂的业务状态机可以放在某个生命周期状态内部。

三、四个主状态（Primary States）

Unconfigured（未配置）

节点刚实例化后的状态，没有应保留的配置状态。configure 可进入配置流程；也可以直接 shutdown。

Inactive（非活动）

节点不执行业务处理，不读取或处理托管 topic 数据，也不响应托管服务请求。适合修改参数、发布/订阅关系及其他配置。可 activate、cleanup 或 shutdown。

Active（活动）

节点正常工作：读取并处理数据、发布输出、响应服务请求。可 deactivate 或 shutdown；不可处理的错误会触发 ErrorProcessing。

Finalized（已终结）

销毁前的终态，只能执行 destroy。它故意保留失败节点，便于调试、状态检查，或由 supervisor 按策略重建。

四、六个过渡状态（Transition States）

过渡状态执行的回调成功结果失败/异常
ConfiguringonConfigure：加载配置、建立长期资源和通信实体Inactive明确失败回 Unconfigured；其他错误进 ErrorProcessing
CleaningUponCleanup：清空状态，恢复到类似刚创建的状态UnconfiguredErrorProcessing
ActivatingonActivate：取得仅在工作时需要的资源，完成启动准备ActiveErrorProcessing
DeactivatingonDeactivate：撤销激活阶段的改变，释放活动资源InactiveErrorProcessing
ShuttingDownonShutdown：执行销毁前清理；回调可知道来源状态FinalizedErrorProcessing
ErrorProcessingonError：清理错误现场并尝试恢复Unconfigured无法完整清理则 Finalized

五、图中管理动作与事件

动作含义
create实例化节点；设计上除构造函数外不执行额外代码。
configure / cleanup建立或清除长期配置资源，在 Unconfigured 与 Inactive 之间循环。
activate / deactivate开始或停止业务处理，在 Inactive 与 Active 之间切换。
shutdown从除 Finalized 外的主状态进入关闭流程，最终到 Finalized。
destroy释放节点对象；通常对应析构函数或标准 deallocation。
lifecycle_state状态变化事件。应广播最终状态、转换和结果码，并在每次转换触发时发布。

六、对导航系统的实际启示

对导航栈而言，可以把地图、传感器、规划器和控制器的资源准备放入配置阶段，把硬件占用或实时处理放入激活阶段；需要重载参数或替换组件时先停到 Inactive，再 cleanup/configure；发生不可恢复异常时保留 Finalized 状态，让管理器记录原因并按策略销毁、重建。这样“节点是否已启动”和“节点是否允许执行任务”就不再是同一个模糊概念。

仿真规则与原设计图的区别
此仿真采用 ROS 2 rcl 默认状态机：configure、activate、deactivate、cleanup 的 FAILURE 返回原主状态；shutdown 的 SUCCESS 和 FAILURE 均到 Finalized。ERROR 进入 ErrorProcessing；on_error 成功到 Unconfigured，失败或错误到 Finalized。原设计文档较早，部分失败路径与当前实现有差异。普通业务回调抛异常并不保证所有客户端库都会自动进入 ErrorProcessing；这里仅模拟生命周期转换回调的 ERROR。
Active 也不代表框架自动屏蔽所有普通订阅、服务或定时器；开发者需要在节点实现中管理这些业务行为。

  
外部管理器调用例程

  

  

  
前提：已 source ROS 2 环境，目标是开启生命周期服务的节点，且正在 spin。两个终端使用相同的 ROS_DOMAIN_ID。可以在另一个终端运行官方示例（需要安装 lifecycle 包）：ros2 run lifecycle lifecycle_talker，默认节点名为 /lc_talker。下列四种方式是替代方案，同一转换成功后不要重复执行。

  

  

  
C++ 构建方式
创建 ament_cmake 包，将 C++ 示例保存为包内的 src/lifecycle_client.cpp：
ros2 pkg create --build-type ament_cmake lifecycle_manager_demo --dependencies rclcpp lifecycle_msgs
在 CMakeLists.txt 的 ament_package() 之前加入：
find_package(rclcpp REQUIRED)
find_package(lifecycle_msgs REQUIRED)
add_executable(lifecycle_client src/lifecycle_client.cpp)
ament_target_dependencies(lifecycle_client rclcpp lifecycle_msgs)
install(TARGETS lifecycle_client DESTINATION lib/${PROJECT_NAME})
在工作区根目录执行：
colcon build --packages-select lifecycle_manager_demo
source install/setup.bash
ros2 run lifecycle_manager_demo lifecycle_client

  
转换 ID：configure = 1，cleanup = 2，activate = 3，deactivate = 4；shutdown 从 Unconfigured / Inactive / Active 发起时分别为 5 / 6 / 7。创建节点由程序或 launch 完成，销毁由对象所有者完成；Finalized 不等于进程已退出。

nav2_util::LifecycleNode 在原生生命周期节点之上，为 Nav2 节点提供共同的连接维护与退出清理机制。阅读时抓住三个问题：它继承了什么？Bond 何时建立和释放？Context 关闭前如何清理？


  
一、继承关系：保留原生状态机，补充公共机制

  
  
头文件使用 public 继承；实现文件的构造函数把节点名称、命名空间和 NodeOptions 传给原生基类。因此生命周期的状态、转换和管理接口沿用 ROS 2 的机制，这层封装没有新增主状态，也不会自动执行 configure 或 activate。

  
// lifecycle_node.hpp：公开继承原生节点
class LifecycleNode : public rclcpp_lifecycle::LifecycleNode
{
  // Nav2 公共机制
};

// lifecycle_node.cpp：构造函数初始化列表
: rclcpp_lifecycle::LifecycleNode(node_name, ns, options)

  
业务节点仍负责：实现配置、激活、停用和清理回调中的业务逻辑，例如创建通信对象、启动处理、停止任务和释放资源。Nav2 基类提供公共机制，不自动完成这些业务操作。


  
二、Bond 心跳连接：维护节点与管理器之间的连接

  
  
关键位置源码行为如何理解

    
构造函数声明并设置禁用心跳超时的参数为 true。节点侧不会因管理器心跳超时而自行判定连接失败。管理器侧的检测和恢复策略不在这两个文件中。

    
createBond()创建 Bond 对象，使用主题名 bond、节点名作为标识、当前节点共享指针；设置周期 0.10 秒、超时值 4.0 秒，然后 start()。提供建立连接的公共方法。构造函数没有调用它，具体业务节点需在合适时机主动调用。

    
destroyBond()若 bond_ 存在，调用 reset()。释放连接对象；Context 关闭前的回调也会主动调用此方法。

  

  
// createBond() 的核心实现
bond_ = std::make_unique<bond::Bond>(
  std::string("bond"), this->get_name(), shared_from_this());
bond_->setHeartbeatPeriod(0.10);
bond_->setHeartbeatTimeout(4.0);
bond_->start();

// destroyBond() 的核心实现
if (bond_) {
  bond_.reset();
}

  
注意这两个细节：节点侧超时判断已被禁用，因此 4.0 秒不能解读为“节点会在 4 秒后自动退出”；createBond() 使用 shared_from_this()，应在对象已有有效共享所有权后调用，不应直接搬到构造函数里执行。


  
三、退出清理：在 Context 关闭前尽力停用、清理资源

  
  
时机执行顺序作用

    
节点构造时register_rcl_preshutdown_callback() 向节点所属 Context 注册回调并保存句柄。让节点能在 Context 尚未关闭时获得清理机会。

    
Context 关闭前on_rcl_preshutdown() → runCleanups() → destroyBond()。先尝试停用与清理，再释放心跳连接。

    
节点析构时再次调用 runCleanups()；若回调句柄存在，将其从 Context 移除并释放句柄。执行兜底清理，并解除绑定 this 的回调注册。

  

  
// runCleanups()：源码中的两个独立 if
if (get_current_state().id() ==
  lifecycle_msgs::msg::State::PRIMARY_STATE_ACTIVE)
{
  this->deactivate();
}

if (get_current_state().id() ==
  lifecycle_msgs::msg::State::PRIMARY_STATE_INACTIVE)
{
  this->cleanup();
}

  
若 deactivate() 成功进入 Inactive，紧接着就会执行 cleanup()；若停用后仍为 Active 或进入其他状态，第二个条件就不成立。这是源码所说的 best effort（尽力清理）：没有重试，也没有覆盖所有过渡状态。

  
Context 退出不等于生命周期 shutdown。这条路径没有主动调用 shutdown()，不以进入 Finalized 为目标。应优先在对象完整存活时完成正常停用和清理；基类析构阶段受 C++ 虚函数分派规则限制，不能保证派生类业务清理回调完整执行。
