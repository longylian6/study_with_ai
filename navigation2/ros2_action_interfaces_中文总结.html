ROS 2 Action 底层接口展开

本文以 navigation_manager_msgs/action/TaskCommand.action 为例，说明一个 ROS 2 Action 对外暴露的 3 个 Service 和 2 个 Topic。

原始 Action 定义

# Goal
string goal       # 任务 JSON
---
# Result
string result     # 本条命令的最终结果 JSON
---
# Feedback
string feedback   # 本条命令的进度 JSON

接口总览

以下以 Action Server 名称 /navigation_manager/task 为例；ROS 2 会在该名称下生成 3 个 Service 和 2 个 Topic。

类别实际名称（默认命名）接口类型用途
Service/navigation_manager/task/_action/send_goalnavigation_manager_msgs/action/TaskCommand_SendGoal提交目标并返回是否接受。
Service/navigation_manager/task/_action/get_resultnavigation_manager_msgs/action/TaskCommand_GetResult按 Goal UUID 获取最终结果。
Service/navigation_manager/task/_action/cancel_goalaction_msgs/srv/CancelGoal请求取消一个或多个目标。
Topic/navigation_manager/task/_action/feedbacknavigation_manager_msgs/action/TaskCommand_FeedbackMessage发布目标执行过程中的反馈。
Topic/navigation_manager/task/_action/statusaction_msgs/msg/GoalStatusArray发布目标状态数组。

简单说：上表里 TaskCommand_SendGoal、TaskCommand_GetResult、TaskCommand_FeedbackMessage 这几个类型是「自动生成」的，磁盘上并没有同名的 .srv / .msg 文件。你只需要写一个 TaskCommand.action 文件，ROS 编译时就会自动变出这些类型；只有 action_msgs/srv/CancelGoal 和 action_msgs/msg/GoalStatusArray 是真实存在的通用文件。

生成规则与本仓库说明

  • Action 的 Goal、Result、Feedback 会生成 TaskCommand_Goal、TaskCommand_Result、TaskCommand_Feedback。
  • 本包的 Action Server 名称为 /navigation_manager/task。
  • TaskCommand.action 的三个业务字段均为 string：goal、result、feedback。
  • 修改 .action 后需要重新构建接口包并重新 source 工作空间。

C++ Action Server

Executor、Callback Group 与两个 Client 的回调顺序

项目本例默认行为
Action Server 的 Callback Groupcreate_server() 未传入 Callback Group，因此加入 Node 的默认组；默认组类型是 MutuallyExclusive，同一时刻最多执行其中一个回调。
ExecutorAction Server 不创建也不指定 Executor。若 main() 使用常见的 rclcpp::spin(node)，节点由 SingleThreadedExecutor 驱动。
execute()本例在 accepted() 中创建独立线程，因此 Goal A、B 的业务执行可以并发；它们已不受 Executor 和默认 Callback Group 串行约束。

Client A、B 几乎同时调用 async_send_goal() 时，DDS 请求的实际到达/取出顺序没有固定保证。默认配置下，每个已接受 Goal 的 goal() 与紧随其后的 accepted() 位于同一次 Action Server 请求处理链中，不会被另一个 Goal 回调插入。

可能顺序 1：先处理 A

TaskServer::goal(A)
↓ A 返回 ACCEPT_AND_EXECUTE
TaskServer::accepted(A)
↓
TaskServer::goal(B)
↓ B 返回 ACCEPT_AND_EXECUTE
TaskServer::accepted(B)

可能顺序 2：先处理 B

TaskServer::goal(B)
↓ B 返回 ACCEPT_AND_EXECUTE
TaskServer::accepted(B)
↓
TaskServer::goal(A)
↓ A 返回 ACCEPT_AND_EXECUTE
TaskServer::accepted(A)

拒绝分支：如果 goal(A) 返回 REJECT，就不会执行 accepted(A)。若显式改用 Reentrant Callback Group 并配合 MultiThreadedExecutor，A、B 的处理可能并发交错，不能再依赖上面的成对串行顺序。

为什么 accepted() 必须快速返回？

goal() 和 accepted() 都由 Executor 驱动。若在其中直接执行耗时任务，默认互斥组会阻塞后续 Goal、Cancel 等 Action 通信。因此本例只在 accepted() 中启动工作线程，然后立即返回。

rclcpp_action::GoalResponse 返回值

返回值含义accepted()SendGoal.Response.accepted
REJECT拒绝 Goal，Client 收到拒绝响应不会调用false
ACCEPT_AND_EXECUTE接受并立即执行自动调用true
ACCEPT_AND_DEFER接受但暂不执行，Server 稍后决定何时执行自动调用true

SendGoal.Response.accepted 只表示是否接受 Goal，无法区分“立即执行”和“暂不执行”。

rclcpp_action::CancelResponse 返回值

返回值含义CancelGoal.Response.return_code
ACCEPT接受取消请求，Goal 进入取消流程ERROR_NONE (0)
REJECT拒绝取消请求，Goal 继续执行ERROR_REJECTED (1)

处理流程

cancel() 返回值后续处理
ACCEPT返回 ERROR_NONE (0)；Goal 进入 CANCELING；execute() 需检查 is_canceling()，然后调用 canceled(result)，最终进入 CANCELED。
REJECT返回 ERROR_REJECTED (1)；Goal 不进入 CANCELING；execute() 继续执行，之后可调用 succeed() 或 abort()。

ERROR_UNKNOWN_GOAL_ID 和 ERROR_GOAL_TERMINATED 由 Action Server 根据 Goal 状态返回，不是 CancelResponse 的枚举值。

get_result Service 如何处理

Client 在 Goal 被接受后调用 async_get_result()，Server 会自动处理 /navigation_manager/task/_action/get_result 请求。Server 没有单独的用户级 get_result() 回调。

Server 调用get_result.status处理结果
handle->succeed(result)4 STATUS_SUCCEEDED返回成功结果
handle->canceled(result)5 STATUS_CANCELED返回取消结果
handle->abort(result)6 STATUS_ABORTED返回中止结果

如果任务尚未结束，get_result 请求会等待；任务结束后，Action Server 自动返回最终 Result。

#include <chrono>
#include <functional>
#include <memory>
#include "navigation_manager_msgs/action/task_command.hpp"
#include "rclcpp_action/rclcpp_action.hpp"
#include "rclcpp/rclcpp.hpp"

using TaskCommand = navigation_manager_msgs::action::TaskCommand;
using GoalHandle = rclcpp_action::ServerGoalHandle<TaskCommand>;

class TaskServer : public rclcpp::Node {
public:
  TaskServer() : Node("task_server") {
    // 创建 Action Server：自动创建 3 个 Service 和 2 个 Topic。
    server_ = rclcpp_action::create_server<TaskCommand>(
      this, "/navigation_manager/task",
      std::bind(&TaskServer::goal, this, std::placeholders::_1,
        std::placeholders::_2),
      std::bind(&TaskServer::cancel, this, std::placeholders::_1),
      std::bind(&TaskServer::accepted, this, std::placeholders::_1));
  }

private:
  rclcpp_action::GoalResponse goal(
    const rclcpp_action::GoalUUID&,
    std::shared_ptr<const TaskCommand::Goal> goal) {
    // 对应 send_goal Service：接收 Client 发来的 Goal。
    RCLCPP_INFO(get_logger(), "goal: %s", goal->goal.c_str());
    return rclcpp_action::GoalResponse::ACCEPT_AND_EXECUTE;
  }

  rclcpp_action::CancelResponse cancel(
    const std::shared_ptr<GoalHandle>) {
    // 对应 cancel_goal Service：处理 Client 的取消请求。
    return rclcpp_action::CancelResponse::ACCEPT;
  }

  void accepted(const std::shared_ptr<GoalHandle> handle) {
    // Goal 已被 goal() 接受后自动调用；不是一个独立的 Service。
    // 通常在这里启动异步任务，避免阻塞 Action Server 的回调线程。
    std::thread{&TaskServer::execute, this, handle}.detach();
  }

  void execute(const std::shared_ptr<GoalHandle> handle) {
    auto feedback = std::make_shared<TaskCommand::Feedback>();
    for (int i = 0; i <= 10; ++i) {
      if (handle->is_canceling()) {
        // 取消后通过 get_result Service 返回 canceled 结果。
        auto result = std::make_shared<TaskCommand::Result>();
        result->result = "{\"status\":\"canceled\"}";
        handle->canceled(result);
        return;
      }
      // 如果检测到任务异常，通过 get_result Service 返回 aborted 结果。
      if (/* 检测任务异常 */ false) {
        auto result = std::make_shared<TaskCommand::Result>();
        result->result = "{\"status\":\"aborted\",\"reason\":\"task error\"}";
        handle->abort(result);
        return;
      }
      // 对应 feedback Topic：持续向 Client 发布执行进度。
      feedback->feedback = "{\"progress\":" + std::to_string(i * 10) + "}";
      handle->publish_feedback(feedback);
      std::this_thread::sleep_for(std::chrono::milliseconds(100));
    }
    // 对应 get_result Service：标记成功并提供最终 Result。
    auto result = std::make_shared<TaskCommand::Result>();
    result->result = "{\"status\":\"succeeded\"}";
    handle->succeed(result);
    // status Topic 由 rclcpp_action 根据 Goal 状态自动发布。
  }

  rclcpp_action::Server<TaskCommand>::SharedPtr server_;
};

该结构参考 ROS 2 官方 C++ Action Server 教程：创建 Server、处理 Goal/Cancel/Accepted 回调，并在独立执行线程中发布 Feedback 和返回 Result。

C++ Action Client

#include <chrono>
#include <functional>
#include <memory>
#include "navigation_manager_msgs/action/task_command.hpp"
#include "rclcpp_action/rclcpp_action.hpp"
#include "rclcpp/rclcpp.hpp"

using TaskCommand = navigation_manager_msgs::action::TaskCommand;
using GoalHandle = rclcpp_action::ClientGoalHandle<TaskCommand>;

class TaskClient : public rclcpp::Node {
public:
  TaskClient() : Node("task_client") {
    // 创建 Client：自动创建 3 个 Service Client 和 2 个 Topic Subscriber。
    client_ = rclcpp_action::create_client<TaskCommand>(
      this, "/navigation_manager/task");
    timer_ = create_wall_timer(
      std::chrono::milliseconds(500),
      std::bind(&TaskClient::send_goal, this));
  }

private:
  void send_goal() {
    timer_->cancel();
    if (!client_->wait_for_action_server(std::chrono::seconds(5))) {
      RCLCPP_ERROR(get_logger(), "Action server not available");
      rclcpp::shutdown();
      return;
    }

    TaskCommand::Goal goal;
    goal.goal = R"({"command":"navigate","target":"A1"})";

    rclcpp_action::Client<TaskCommand>::SendGoalOptions options;
    // send_goal Service 的响应：Goal 被接受或拒绝。
    options.goal_response_callback =
      [this](GoalHandle::SharedPtr handle) {
        if (!handle) {
          RCLCPP_ERROR(get_logger(), "Goal rejected");
        } else {
          RCLCPP_INFO(get_logger(), "Goal accepted");
        }
      };
    // feedback Topic 的订阅回调：接收 Server 发布的执行进度。
    options.feedback_callback =
      [this](GoalHandle::SharedPtr,
        const std::shared_ptr<const TaskCommand::Feedback> feedback) {
        RCLCPP_INFO(get_logger(), "Feedback: %s",
          feedback->feedback.c_str());
      };
    // get_result Service 的响应：接收最终 Result。
    options.result_callback =
      [this](const GoalHandle::WrappedResult& wrapped_result) {
        RCLCPP_INFO(get_logger(), "Result status: %d",
          static_cast<int>(wrapped_result.code));
        RCLCPP_INFO(get_logger(), "Result: %s",
          wrapped_result.result->result.c_str());
        rclcpp::shutdown();
      };
    client_->async_send_goal(goal, options);
    // status Topic 由 rclcpp_action 内部订阅并跟踪 Goal 状态。
    // 取消时可通过 Goal Handle 调用 async_cancel_goal()，对应 cancel_goal Service。
  }

  rclcpp_action::Client<TaskCommand>::SharedPtr client_;
  rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char ** argv) {
  rclcpp::init(argc, argv);
  rclcpp::spin(std::make_shared<TaskClient>());
  rclcpp::shutdown();
  return 0;
}

Client 完整流程：创建 Node 和 Action Client，等待 Server，发送 Goal，处理 Goal 响应、Feedback 和最终 Result。

Client 使用 async_get_result()

async_get_result() 需要传入 async_send_goal() 返回的 GoalHandle。它对应 get_result Service，返回的 Future 最终得到 WrappedResult。

// goal_handle 必须来自 async_send_goal() 的 Goal Response。
auto goal_handle_future = client_->async_send_goal(goal, options);
if (rclcpp::spin_until_future_complete(
      shared_from_this(), goal_handle_future) !=
    rclcpp::FutureReturnCode::SUCCESS) {
  RCLCPP_ERROR(get_logger(), "Failed to send goal");
  return;
}
auto goal_handle = goal_handle_future.get();
if (!goal_handle) {
  RCLCPP_ERROR(get_logger(), "Goal rejected");
  return;
}

// 发送 get_result Request；Server 结束 Goal 后 Future 才完成。
auto result_future = client_->async_get_result(goal_handle);
if (rclcpp::spin_until_future_complete(
      shared_from_this(), result_future) !=
    rclcpp::FutureReturnCode::SUCCESS) {
  RCLCPP_ERROR(get_logger(), "Failed to get action result");
  return;
}

auto wrapped_result = result_future.get();
switch (wrapped_result.code) {
  case rclcpp_action::ResultCode::SUCCEEDED:
    RCLCPP_INFO(get_logger(), "Succeeded: %s",
      wrapped_result.result->result.c_str());
    break;
  case rclcpp_action::ResultCode::CANCELED:
    RCLCPP_WARN(get_logger(), "Canceled: %s",
      wrapped_result.result->result.c_str());
    break;
  case rclcpp_action::ResultCode::ABORTED:
    RCLCPP_ERROR(get_logger(), "Aborted: %s",
      wrapped_result.result->result.c_str());
    break;
  default:
    RCLCPP_ERROR(get_logger(), "Unknown result code");
    break;
}

SendGoalOptions::result_callback 和手动调用 async_get_result() 是两种写法：二选一，不要对同一个 Goal 重复请求 Result。实际异步程序通常在 Goal Response 回调中保存 GoalHandle，再调用 async_get_result()，避免使用 .get() 阻塞线程。

Client 处理 cancel_goal Service Response

#include "action_msgs/srv/cancel_goal.hpp"

// goal_handle 是 async_send_goal() 返回的 Goal Handle。
// 如果没有调用 async_send_goal() ， async_cancel_goal 不能正常调用
auto cancel_future = client_->async_cancel_goal(goal_handle);
auto response = cancel_future.get();

switch (response->return_code) {
  case action_msgs::srv::CancelGoal::Response::ERROR_NONE:
    RCLCPP_INFO(get_logger(), "Cancel request accepted");
    break;
  case action_msgs::srv::CancelGoal::Response::ERROR_REJECTED:
    RCLCPP_WARN(get_logger(), "Cancel request rejected");
    break;
  case action_msgs::srv::CancelGoal::Response::ERROR_UNKNOWN_GOAL_ID:
    RCLCPP_WARN(get_logger(), "Unknown goal ID");
    break;
  case action_msgs::srv::CancelGoal::Response::ERROR_GOAL_TERMINATED:
    RCLCPP_WARN(get_logger(), "Goal already terminated");
    break;
}

async_cancel_goal() 调用 cancel_goal Service，返回 CancelGoal.Response。ERROR_NONE 只表示取消请求被接受，不代表任务已经完成取消；Server 仍需检查 handle->is_canceling() 并调用 handle->canceled(result)。goals_canceling 列表表示实际进入取消流程的 Goal。

Nav2 Action Server：从通信回调到任务调度

SimpleActionServer<ActionT> 在原生 rclcpp_action::Server 上管理一个 current、一个 pending 和一个异步工作线程。以下按本工作区源码与“nav2仿真”说明； 弹窗展示 GitHub Navigation2 humble 分支的上游源码。

三个回调Goal 时序抢占与 pendingwork() 收尾取消流程停用与线程

封装的目的：让通信回调快速返回，让业务集中在 execute()

层次负责什么设计收益
rclcpp_action / rcl_action3 个 Service、2 个 Topic，UUID、Goal 状态、结果缓存与响应Client 无需知道 Server 是否使用 Nav2 封装
SimpleActionServer默认 Goal / Cancel 策略、current / pending、执行线程和异常收尾避免每个应用重复编写 Goal Handle 管理
用户 execute_callback_()计算路径或执行任务，检查取消 / 抢占 / 停用，发布进度并结束任务把何时切换、如何安全停止留给业务代码

三个 Action 回调并不对应三个 Service：handle_goal() 与 handle_accepted() 都属于提交 Goal 的处理链；handle_cancel() 处理取消。get_result 由底层自动处理，没有额外的用户级 GetResult 回调。

01 · 三个回调：决策、取消许可、安排执行

构造函数将这三个函数绑定到 rclcpp_action::create_server()。下面摘录分支逻辑，省略签名、日志和锁；真实实现使用 update_mutex_ 串行保护这些槽位更新。

handle_goal()

收到 SendGoal 请求时调用。只判断 Server 是否激活，不检查任务 JSON。

if (!server_active_) {
  return GoalResponse::REJECT;
}
return GoalResponse::ACCEPT_AND_EXECUTE;

目的：由 activate / deactivate 控制任务入口。拒绝时 response.accepted=false，不再调用 handle_accepted。

handle_cancel(handle)

底层筛选出可尝试取消的 Goal 后调用，检查传入 Handle 是否仍 active。

if (!handle->is_active()) {
  return CancelResponse::REJECT;
}
return CancelResponse::ACCEPT;

目的：允许取消。ACCEPT 后由底层推进到 CANCELING；这里不停止线程，也不调用 canceled(result)。

handle_accepted(handle)

Goal 接受后自动调用，安排当前或等待槽位，并尽快返回 Executor。

if (is_active(current_handle_) || is_running()) {
  // 已占用的 pending 先 terminate 再替换
  pending_handle_ = handle;
  preempt_requested_ = true;
} else {
  current_handle_ = handle;
  // std::async(std::launch::async, ...)
  execution_future_ = start_work();
}

目的：空闲时启动后台工作，忙时保留最新 pending。start_work() 是图解简写，并非实际 API。

内部返回 / 分支客户端可见业务执行
handle_goal → REJECTSendGoal.accepted=false，空 GoalHandle不执行 accepted / execute
handle_goal → ACCEPT_AND_EXECUTESendGoal.accepted=trueaccepted 再决定 current 或 pending；接受不保证马上处理该任务
handle_cancel → ACCEPT成功推进取消的 Goal 列入 goals_canceling；单 Goal 常见 ERROR_NONE等待 execute 检查并收尾
handle_cancel → REJECT单个活动 Goal 被拒绝时通常 ERROR_REJECTED、空 goals_canceling原任务继续；未知或已终止 Goal 可由底层直接返回其它错误

02 · 一个 Goal 如何从请求进入业务线程

get_result 可能先到、也可能后到：未完成时等待；完成后在结果保留期内返回缓存。封装的成功 / 终止方法通过底层 GoalHandle 提供结果。

03 · 两个槽位：current 正在处理，pending 保留最新请求

一个正在执行的 Goal 不会因新请求到来就被立刻中断。新 Goal 先进入 pending，设置 preempt_requested_=true；业务在合适的检查点决定是否调用 accept_pending_goal()。

① G1 到来current = G1pending = ∅启动工作线程
② G2 到来current = G1pending = G2G1 继续运行
③ G3 到来current = G1pending = G3terminate(G2)：通常 ABORTED
④ 应用接受抢占current = G3pending = ∅旧 G1 ABORTED，清除抢占标志
展开 accept_pending_goal() 的关键实现 
// 摘录：省略锁、日志与无效 pending 检查
if (is_active(current_handle_) && current_handle_ != pending_handle_) {
  current_handle_->abort(empty_result());
}
current_handle_ = pending_handle_;
pending_handle_.reset();
preempt_requested_ = false;
return current_handle_->get_goal();

pending 已经经过 ACCEPT_AND_EXECUTE，ROS Goal 状态可以是 EXECUTING；“等待”指应用槽位，不是 ROS 的 ACCEPTED/DEFER 状态。抢占旧 current 调用的是 abort()，不会向它发送 Cancel 请求。

函数 / 条件实际作用设计目的
is_preempt_requested()只读标志，不自动换任务业务自行选择安全切换点
accept_pending_goal()终止 active 旧 current、接管 pending、清标志，返回新 Goal同一业务回调可继续处理新任务，无需新建线程
terminate_pending_goal()仅终止 pending 并清标志应用可拒绝这次业务切换，保留 current
current active 或 is_running()新 Goal 进入 pending即使 current 已返回结果，仍等旧业务回调退出，避免两个工作线程重叠

pending 只有一个槽位，不是 FIFO 队列。覆盖 pending 时使用 terminate()：若它已 CANCELING 则 CANCELED，否则 ABORTED。

04 · work()：回调返回后，才进入封装的收尾检查

succeeded_current() 只调用 current_handle_->succeed(result) 并清空 current；线程是否结束取决于业务是否 return。若 return 后还有 pending，work 会在原线程重新调用 execute。

completion_callback_ 是异常 / 失败 / 停用收尾通知，不是每次成功后的回调，也不是客户端的 result_callback。本地源码的 work() 部分分支直接调用它而未判空，示例与仿真提供有效回调。

05 · 取消是协作过程：许可 → 检查 → 清理 → 结果

结束方法目标 Handle / 状态规则结果
succeeded_current(result)结束当前 Goal，清空 currentSUCCEEDED
terminate_current(result)只结束 current：CANCELING → canceled，其它 active → abortCANCELED 或 ABORTED
terminate_all(result)对 current / pending 分别执行上述判断，清抢占标志不同 Goal 可以得到不同的终态
publish_feedback(feedback)检查 current active，然后转发到 GoalHandleFeedback Topic；不改变 Goal 终态
本版本细节：is_cancel_requested() 优先查询 pending 
if (current_handle_ == nullptr) {
  return false;
}
if (pending_handle_ != nullptr) {
  return pending_handle_->is_canceling();
}
return current_handle_->is_canceling();

例如 G1=current 且 CANCELING、G2=pending 且 EXECUTING，此查询返回 false，并非两个 Handle 的逻辑“或”。若取消的是 G2，则查询为 true；应用调用 terminate_all() 后，G1 可能 ABORTED、G2 为 CANCELED。

仿真在 CANCELING 后停止生成自动 Feedback，这是示例应用的策略；本地封装 publish_feedback() 仅检查 active，并未自动实施这个策略。在途 Feedback 与取消响应可并行到达。

06 · 生命周期与线程：停用入口，不等于强杀业务

activate()
active=true、stop=false；允许新 Goal。
deactivate()
active=false、stop=true；新 Goal 被拒绝。
等待 future
每 100ms 检查；默认达到 500ms 后 terminate_all 并报告超时。
回调退出
work() 收尾、future ready，deactivate() 才能结束等待。

server_timeout_ 是停用等待的超时检查阈值，不是任务执行时间上限。超时后循环仍等待，后续轮次还可能再次进入超时分支；无法强行终止一个卡住的 execute 回调。

机制实现与目的
spin_thread=false通信回调交给外部 Executor；任务仍通过 std::async 在后台执行
spin_thread=true单独的 MutuallyExclusive callback group + SingleThreadedExecutor + NodeThread 驱动通信；后台业务线程另算
is_running()检查 execution_future_.valid() 且 wait_for(0) 为 timeout；它反映线程工作是否未结束，不等同于 current 非空
recursive_mutex保护槽位和标志更新，允许 terminate_all → terminate 等内部嵌套加锁；不意味着应用的全部资源自动线程安全

应用通常在节点生命周期回调中调用 activate / deactivate；SimpleActionServer 自身不是 LifecycleNode。执行逻辑应分段工作并检查 is_server_active()、取消与抢占，及时清理后 return。

应用执行循环的结构示意（需实现其中的业务函数） 
// 伪代码：process_one_step / cleanup / restart_task 由应用实现。
// 每一轮都应能及时返回；实际项目还需处理取消与完成的并发竞争。
auto goal = server_->get_current_goal();
while (rclcpp::ok()) {
  if (!server_->is_server_active()) {
    cleanup();
    server_->terminate_all();
    return;
  }
  if (server_->is_cancel_requested()) {
    cleanup();
    server_->terminate_all();
    return;
  }
  if (server_->is_preempt_requested()) {
    goal = server_->accept_pending_goal();
    restart_task(goal);
  }
  if (process_one_step(goal)) {  // true 表示本次任务完成
    auto result = std::make_shared<TaskCommand::Result>();
    result->result = R"({"status":"succeeded"})";
    server_->succeeded_current(result);
    return;  // 让 work() 接续 pending 或结束线程
  }
  // 按业务频率发布反馈、等待下一轮；避免忙循环。
}

源码细节与演示约定
  • handle_goal() 仅按 server_active_ 接受或拒绝，不检查 goal JSON。pending 也已返回 ACCEPT_AND_EXECUTE；它的 ROS 状态为 EXECUTING，但应用尚未切换过去。
  • pending 是单个槽位。第三个 Goal 到来会 terminate(pending_handle_) 再替换；accept_pending_goal() 对仍 active 的旧 current 直接调用 abort(empty_result())，并非取消协议。
  • 本版本 is_cancel_requested()：current 为空则 false；pending 非空则只查 pending；否则查 current。可用“pending 存在时，取消 current”场景观察。演示的“检查取消”按钮参考 PlannerServer：检查为 true 后 terminate_all() 并 return。
  • terminate() 对 CANCELING Goal 调用 canceled()，对其它 active Goal 调用 abort()。接受取消只改变状态；后续 Result 没有固定 50ms 延迟。
  • work() 在用户回调返回后检查 stop、兜底终止未完成 current、接续 pending。异常分支终止全部并退出线程。本演示提供有效的 completion_callback_ 并计数；本地源码的部分分支未检查其是否为空。
  • deactivate() 设置 active=false、stop=true，每 100ms 检查线程；达到默认 500ms 后终止 Goal 并报错，仍继续等待，不能强杀用户回调。演示允许手动 return，观察线程最终退出。
  • 本演示采用 spin_thread=true：通信由独立 Executor 处理，工作由 std::async 执行。即使 spin_thread=false，业务工作仍在异步线程。互斥锁竞争、网络丢包和结果缓存过期不在此仿真范围。
